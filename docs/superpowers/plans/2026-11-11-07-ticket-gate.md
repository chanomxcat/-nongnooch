# Ticket & Gate: ออกบัตร Ed25519, Gate API, Transfer Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** service `ticket` ออก e-Ticket รายใบพร้อม QR Ed25519 จาก `order.paid` ภายใน 30 วินาที, void บัตรเมื่อคืนเงิน, เปิดใช้บัตรรายปี 365 วันพร้อมรูปผู้ถือ, ให้ Gate Scanner ดึง snapshot ไปตรวจ offline และส่งผลสแกนแบบ online / batch (กันใช้ซ้ำข้ามประตู), ส่งบัตรให้เพื่อน (F11), ค้นหาบัตร + ปล่อยผ่านด้วยมือที่ประตู และส่งยอดเข้าประตู / สถานะบัตรไประบบเดิม (mockext `/legacy`)

**Architecture:** service `ticket` (schema `ticket`) บน chassis ของ Plan 01 รับ `order.paid` / `order.refunded` ผ่าน `consumer.Run` เขียนบัตร + outbox ใน transaction เดียว เปิด gRPC `TicketService` ให้ Commerce (`GetTickets`, `VoidTickets`) และเรียก gRPC `MemberService.GetMemberByContact` ของ Member ตอนส่งบัตร / ค้นหาบัตร การสแกนทุกแบบ (QR online, batch offline, ปล่อยผ่านด้วยมือ) วิ่งผ่านฟังก์ชันเดียว `Gate.Scan` ที่ล็อกแถวบัตรด้วย `SELECT … FOR UPDATE` จึงมีผู้ชนะคนเดียวเสมอ การส่งข้อมูลไประบบเดิมใช้ตาราง `legacy_sync` ที่เขียนใน transaction เดียวกับการเปลี่ยนสถานะ แล้วมี worker ส่งพร้อม retry

**Tech Stack:** Go 1.23 + chassis (Plan 01), `crypto/ed25519`, `encoding/base64` (`RawURLEncoding`), `google.golang.org/grpc`, `github.com/minio/minio-go/v7`, `github.com/nyaruka/phonenumbers`, `time/tzdata`

**Spec:** [docs/system-design.md](../../system-design.md) F4, F11, S3 (ขั้น 25–36), S4 (คืนเงิน), S5, หัวข้อ 2 แถว "QR e-Ticket" และ "Gate Scanner" · [ROADMAP.md](../../../roadmap/ROADMAP.md) 4.2 E4 และ E2 แถว "ส่งบัตรให้เพื่อน" · [contracts](2026-11-11-contracts.md) หัวข้อ 4, 5, 6, 7 · ขึ้นกับ [Plan 01](2026-11-11-01-platform-chassis.md), [Plan 00](2026-11-11-00-mock-external.md) Task 5 (`/legacy`), Plan 03 (`MemberService`), Plan 12 Task 1 (`pkg/chassis/authn`) · ผู้ใช้ API ฝั่ง Gate: Plan 14

**ค่าที่แผนนี้กำหนดเพิ่ม เพราะ spec ไม่ได้ระบุ (ให้ PO ยืนยันใน review):**
- บัตร `restaurant` / `show` ออกเป็นแถว Ticket พร้อม QR (`k` = kind, `d` = visitDate) ไว้สแกนรับสิทธิ์ที่ห้องอาหาร / โรงแสดง ส่วนประตูทางเข้าสวนตอบ `invalid` (`not_gate_ticket`)
- บัตรรายปี: เปิดใช้โดยเจ้าของบัตรเท่านั้น ต้องอัปโหลดรูปก่อน, `validFrom` = วันเปิดใช้ (Bangkok), `validUntil` = `validFrom` + 364 วัน (นับรวม 365 วัน), สแกนผ่านได้ 1 ครั้งต่อวัน (ครั้งที่สองของวันเดียวกันได้ `used`)
- รูปผู้ถือบัตร: JPEG / PNG ไม่เกิน 5 MB
- ส่งบัตรให้เพื่อน: เฉพาะสมาชิก (`mid` ไม่ว่าง), ส่งได้ถึง 08:00 Asia/Bangkok ของ `visitDate` (`TRANSFER_CUTOFF=08:00`), `TRANSFER_MAX=1`, บัตรรายปีส่งได้เฉพาะก่อนเปิดใช้ (บัตรรายปีที่ซื้อเป็นของขวัญออกให้ผู้รับตั้งแต่แรกตาม `order.paid.items[].gift`), บัตรราคาไทยส่งแบบลิงก์ไม่ได้
- batch สแกน offline: ไม่เกิน 500 รายการต่อคำขอ, `scannedAt` ต้องไม่เกินเวลารับ + 10 นาที และไม่เก่ากว่า 7 วัน
- ค้นหาบัตรที่ประตู: คืนไม่เกิน 50 ใบ
- ส่งระบบเดิม: retry หน่วง 2^attempts วินาที สูงสุด 1 ชั่วโมง ครบ 20 ครั้งแจ้ง on-call แต่ยัง retry ต่อ

## Review Focus

1. **สองประตูสแกนบัตรใบเดียวกันพร้อมกัน (online):** ต้องได้ `ok` หนึ่งครั้งพอดี ที่เหลือได้ `used` พร้อมเวลาและประตูที่ใช้ ไม่ใช่ `ok` สองครั้ง (Task 5 `TestConcurrentScansOneOK`, Task 6 `TestBatchConcurrentWithOnline`)
2. **ประตู offline ปล่อยผ่านบัตรใบเดียวกัน แล้ว upload ทีหลัง หรือ upload batch เดิมซ้ำเพราะ timeout:** รายการหลังต้องติดธง `duplicate=true` และอ้างถึงการสแกนครั้งแรก ส่วน batch ที่ส่งซ้ำต้องได้ผลเดิม ไม่เกิด GateScan / `ticket.scanned` เพิ่ม (Task 6 `TestBatchCrossGateDuplicate`, `TestBatchTwoOfflineGates`, `TestBatchReuploadIdempotent`)
3. **upload batch หลังเที่ยงคืน:** บัตรที่สแกนตอน 23:50 แต่ส่งขึ้นตอน 00:30 ต้องตัดสินด้วยวันที่ของ `scannedAt` (Bangkok) ไม่ใช่วันที่รับ ไม่อย่างนั้นจะได้ `wrong_date` ผิด ๆ (Task 6 `TestBatchAfterMidnightUsesScanDate`) และ snapshot ที่ไม่ส่ง `date` ต้องใช้วันของ Bangkok ไม่ใช่ UTC (Task 5)
4. **`order.paid` ของออเดอร์เดียวมาสองครั้งคนละ event id** (Webhook + กระทบยอด S4): ต้องได้บัตรชุดเดียวและ `ticket.issued` ครั้งเดียว (Task 2 `TestIssueIdempotentByOrderID`)
5. **คืนเงินมาก่อนออกบัตร หรือแข่งกับการสแกน / การส่งบัตร:** `VoidTickets` ที่มาก่อน `order.paid` ต้องทำให้บัตรที่ออกทีหลังเป็น `void` ทันที, ส่งบัตรพร้อมกับสแกนต้องได้สถานะที่สอดคล้องกัน และบัตรใบใหม่จากการส่งต่อต้องถูก void เมื่อคืนเงินออเดอร์เดิม (Task 3 `TestVoidBeforeIssueTombstone`, Task 7 `TestTransferVsScanRace`, `TestRefundVoidsReplacementTicket`)

  - `func LoadSigner(pemPKCS8 string, previous []ed25519.PublicKey) (*Signer, error)` · `func (s *Signer) Sign(p QRPayload) (string, error)` · `func (s *Signer) PublicKeys() []ed25519.PublicKey` (ตัวแรก = key ปัจจุบัน ตามด้วย `TICKET_PREVIOUS_PUBLIC_KEYS`)
  - `func ParseQR(qr string, pubs []ed25519.PublicKey) (QRPayload, error)` ผ่านถ้าลายเซ็นตรงกับ key ใดก็ได้ในรายการ · error: `ErrQRFormat` (prefix ไม่ใช่ `NN1`, ไม่ครบ 3 ส่วน, b64 / JSON เสีย, `k` ไม่อยู่ใน `day|annual|restaurant|show`), `ErrQRSignature`
  - `func BangkokDate(t time.Time) string` (`YYYY-MM-DD`) และ `func BangkokTime(date, hhmm string) (time.Time, error)` main ต้อง `import _ "time/tzdata"` เพราะ image distroless ไม่มี zoneinfo
  - `qr_vectors.json`: `{"publicKeys":["<b64url 32 byte>", …],"cases":[{"name","qr","valid":bool,"payload"?}]}` อย่างน้อย (ชื่อ case ตามที่ Plan 14 ใช้) `day_valid`, `annual_valid` (`d` null), `restaurant_valid`, `show_valid`, `second_key_valid` (ลงนามด้วย key ตัวที่สองในรายการ), `tampered_payload` (แก้ 1 byte), `wrong_key` (key ที่ไม่อยู่ในรายการ), `prefix_NN2`
- ตาราง (ทุกตาราง `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4`):

```sql
  order_item_id CHAR(36) NULL UNIQUE, source_item_id CHAR(36) NOT NULL,  -- order item ต้นทาง บัตรที่ส่งต่อได้ค่าเดิม
  product_id CHAR(36) NOT NULL,

  holder_name VARCHAR(200) NOT NULL, holder_nationality VARCHAR(2) NOT NULL, holder_id_last4 VARCHAR(4) NOT NULL,
  thai_price BOOL NOT NULL, status VARCHAR(12) NOT NULL, qr VARCHAR(512) NOT NULL,
  used_at DATETIME(6) NULL, used_gate_id VARCHAR(32) NULL, void_reason VARCHAR(32) NULL,
  status_changed_at DATETIME(6) NOT NULL,

  transfer_count TINYINT NOT NULL DEFAULT 0, replaces_id CHAR(36) NULL, replaced_by_id CHAR(36) NULL,
  created_at DATETIME(6) NOT NULL,
  INDEX idx_order (order_id, source_item_id), INDEX idx_order_no (order_no), INDEX idx_owner_member (owner_member_id),
  INDEX idx_owner_contact (owner_contact), INDEX idx_visit (visit_date, status), INDEX idx_status (status, status_changed_at)

```
