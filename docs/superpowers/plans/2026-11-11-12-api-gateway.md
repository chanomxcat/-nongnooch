# API Gateway + authn Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** ทางเข้าเดียวของทุก client ที่ `http://localhost:8000/api/<svc>/...` ตรวจ JWT (EdDSA ผ่าน JWKS ของ identity) แล้วส่ง header ตัวตนต่อให้ service, route ไป 8 service, บล็อก `/internal/*`, rate limit ต่อ IP, ตรวจ access token ของ Waiting room ก่อน `POST /api/commerce/orders`, CORS สำหรับ web / admin / gate และรวม OpenAPI ไว้ที่ `/api/docs` พร้อมแพ็กเกจ `pkg/chassis/authn` ที่ service ใช้อ่านตัวตน

**Architecture:** เขียนเองใน Go (`services/gateway`) ด้วย `net/http/httputil.ReverseProxy` เป็น middleware chain: recover → request id → CORS → client IP → rate limit → resolve route (บล็อก internal) → body limit → JWT + strip / inject header → waiting room → proxy ส่วน JWKS เก็บใน cache ที่ refresh ตามรอบและเมื่อเจอ `kid` ใหม่ OpenAPI รวมตอน `make gen` เป็นไฟล์ JSON ที่ embed ใน binary

**ตัดสินใจ Q19 สำหรับ demo: Go เขียนเอง** เพราะ (1) ต้องมีตรรกะเฉพาะ คือ strip / inject header ตาม contracts, ตรวจ waiting-room token ด้วยโค้ดที่ commerce ใช้ร่วม (`pkg/chassis/queuetoken`) และรวม OpenAPI ซึ่ง Traefik / Kong ต้องเขียน plugin (Yaegi / Lua / Go plugin server) อยู่ดี (2) ทีมเขียน Go อยู่แล้ว ใช้ chassis (obs, Dockerfile) เดิมได้ ไม่เพิ่มภาษาหรือ config DSL (3) เป็น binary เดียวใน compose ทดสอบด้วย `httptest` ได้ทั้งหมด ข้อเสียคือต้องดูแลเอง ถ้า production ต้องการ feature ระดับ Kong (plugin, admin API) ให้ทบทวน Q19 อีกครั้ง โดย service ไม่ต้องแก้เพราะสัญญาอยู่ที่ header

**Tech Stack:** Go 1.23 (`net/http`, `net/http/httputil`, `crypto/ed25519`), `github.com/golang-jwt/jwt/v5`, `golang.org/x/time/rate`, `gopkg.in/yaml.v3` (เครื่องมือรวม OpenAPI), chassis `pkg/chassis/obs`, `otelhttp`

**Spec:** [docs/system-design.md](../../system-design.md) หัวข้อ 1.2, หัวข้อ 2 (API Gateway, Edge), O2, S6, Q9, Q19 · [contracts](2026-11-11-contracts.md) หัวข้อ 2, 3, 8 · ขึ้นกับ [Plan 01](2026-11-11-01-platform-chassis.md), [Plan 02](2026-11-11-02-identity-otp.md) Task 3–4 (claims, JWKS) · Plan 06 เป็นเจ้าของรูปแบบ waiting-room token

- contracts หัวข้อ 2: route สาธารณะ (ไม่ต้องมี JWT) ตามรายการใน contracts, `POST /api/report/analytics/collect` rate limit 60 ครั้งต่อนาทีต่อ IP · `X-Client-IP` มาจาก `X-Forwarded-For` เฉพาะ request จาก `TRUSTED_PROXIES` (ค่าเริ่ม Caddy + container `web`, `admin`, `gate`) โดยเลือก IP ขวาสุดที่ไม่อยู่ใน trusted list
- Plan 02: `iss` = `nongnooch-identity`, `aud` = `nongnooch-api`, header `kid`
- S6: "FE->>GW: POST /orders (แนบ access token) · GW->>GW: ตรวจ token ก่อน route" · contracts หัวข้อ 8: token ส่งใน header `X-Queue-Token` ตรวจด้วย `queuetoken.Verify(token string, pub ed25519.PublicKey, now time.Time) (Claims, error)` ด้วย public key จาก env `QUEUE_ACCESS_PUBLIC_KEY`, route ที่ตรวจตาม `QUEUE_PROTECTED_ROUTES` (ค่าเริ่ม `POST /api/commerce/orders`), error `403 queue_token_required|queue_token_invalid|queue_token_expired`
- CORS: app อยู่ที่ `http://localhost:3000` (web), `:3001` (admin), `:3002` (gate)

**ค่าที่แผนนี้กำหนดเพิ่ม (ให้ PO / TL ยืนยันใน review):** rate limit ทั่วไป 30 req/s burst 60 ต่อ IP, `POST /api/identity/auth/*` 2 req/s burst 10 ต่อ IP, IP ใน `RATE_LIMIT_EXEMPT_CIDRS` ไม่จำกัด (เช่น Wi-Fi ในสวนที่กรุ๊ปทัวร์ใช้ IP เดียวกัน), body สูงสุด 1 MB ยกเว้น `/api/content/admin/media` 21 MB, timeout ต่อ upstream 30 วินาที (media 120 วินาที), JWKS refresh ทุก 10 นาทีและเมื่อเจอ kid ใหม่ได้ไม่เกิน 1 ครั้งต่อ 30 วินาที, leeway ของ `exp` / `nbf` 30 วินาที

## Review Focus

1. **ปลอม header ตัวตน:** client ส่ง `X-Roles: admin` / `X-User-Type: staff` มาเองโดยไม่มี token ต้องถูกลบก่อนถึง service (Task 3, 4)
2. **เลี่ยงการบล็อก `/internal`:** `/api/content/internal/seed`, `/api/content//internal/seed`, `/api/content/./internal/seed`, `/api/content/%69nternal/seed`, `/api/content/Internal/seed` และ `%2F` ใน path ต้องไม่ถึง service (Task 3)
3. **identity ล่ม / หมุน key:** JWKS ดึงไม่ได้ต้องใช้ key เดิมใน cache ต่อ, token ที่ `kid` ใหม่ต้องผ่านหลัง refresh และ token ปลอม `kid` สุ่มจำนวนมากต้องไม่ทำให้ยิง identity ถี่ (Task 4)
4. **กรุ๊ปทัวร์ใช้ IP เดียวกัน / ปลอม `X-Forwarded-For`:** IP มาจาก `RemoteAddr` และเชื่อ `X-Forwarded-For` เฉพาะเมื่อ request มาจาก `TRUSTED_PROXIES` (เลือก IP ขวาสุดที่ไม่อยู่ใน trusted list) และมี CIDR ยกเว้น (Task 5)
5. **upstream ล่มหรือช้า / ไฟล์ใหญ่:** ต้องได้ JSON `502 upstream_unavailable` / `504 upstream_timeout` ไม่ใช่หน้า HTML หรือค้าง และ body เกินกำหนดได้ `413` ก่อนส่งต่อ (Task 3)
