## 1. เป้าหมายและหลักการ

### เป้าหมาย

**เป้าหมายหลัก:** รวบรวมข้อมูลนักท่องเที่ยวผ่านการสมัครสมาชิกกับสวนนงนุช เพื่อให้เกิดการกลับมาเที่ยวซ้ำ โดยสมาชิกได้รับพ้อยและโปรโมชันเมื่อกลับมาใช้บริการอีก

ปัจจุบันนักท่องเที่ยวต่างชาติส่วนใหญ่ซื้อบัตรผ่าน Agent นงนุชจึงเข้าไม่ถึงข้อมูลของกลุ่มนี้ โครงการจึงให้ Agent (ผ่านไกด์) เป็นผู้ชวนนักท่องเที่ยวสมัครสมาชิกด้วย Invite code และได้พ้อยตอบแทน

| เป้าหมาย | ความหมาย |
|---|---|
| ฐานสมาชิกของนงนุชเอง | นักท่องเที่ยวทุกกลุ่ม (ซื้อออนไลน์ เคาน์เตอร์ และผ่าน Agent) สมัครสมาชิกและให้ความยินยอมรับข่าวสาร |
| การกลับมาเที่ยวซ้ำ | สมาชิกสะสมพ้อยและได้โปรโมชันเมื่อกลับมา (เปิดแลกพ้อยในเฟส 2) |
| Agent เป็นพันธมิตรหาสมาชิก | ไกด์ได้พ้อยเมื่อนักท่องเที่ยวสมัครด้วย Invite code ของตน |
| ขายผ่านดิจิทัลมากขึ้น | ขายบัตร บัตรห้องอาหาร และการแสดง ผ่าน Website และ App |
| Sponsor และ Partner | ช่องทางรายได้ใหม่ ที่นงนุชอนุมัติทุกรายการก่อนเผยแพร่ (เฟส 3 ถึง 4) |

### หลักการที่ใช้ตัดสินใจตลอดโครงการ

1. **นงนุชเป็นเจ้าของทุกอย่าง** ได้แก่ Domain, App Store, Google Play, Huawei AppGallery, Cloudflare, Firebase, Payment Merchant, Source code และข้อมูลลูกค้า ทุกบัญชีเปิดในนามนงนุช WV ได้รับสิทธิ์เข้าถึงในฐานะผู้พัฒนา ส่วน Cloud เลือกได้ 3 รูปแบบ (หัวข้อ 9.1) แต่ทุกรูปแบบข้อมูลเป็นของนงนุชและย้ายออกได้
2. **เงินเข้านงนุชโดยตรง** ทุกการชำระเงินเข้าบัญชี Merchant ของนงนุช WV ไม่รับเงินแทน
3. **อนุมัติก่อนเผยแพร่** ราคา โปรโมชั่น กติกาพ้อย และโฆษณาทุกรายการผ่าน Workflow อนุมัติใน CMS
4. **เฟส 1 ทำเฉพาะสิ่งที่ต้องพร้อมในวันเปิดตัว** คือขายบัตร สมัครสมาชิก สะสมพ้อย และ Agent Program ฟีเจอร์อื่นย้ายไปเฟสถัดไป
5. **ไม่บังคับโหลด App** ทุกอย่างของเฟส 1 (สมัครสมาชิก กรอก Invite code ซื้อบัตร ดูพ้อย) ทำได้บนเว็บ Mobile App เปิดพร้อมกันเป็นช่องทางเสริม เพราะนักท่องเที่ยวจีนจำนวนมากโหลด App จาก Google Play ไม่ได้
6. **สะสมก่อน แลกทีหลัง** เฟส 1 สะสมพ้อยได้แต่ยังแลกไม่ได้ เปิดแลกในเฟส 2 หลังตรวจข้อมูลจริงและกำหนดมูลค่าพ้อยแล้ว
7. **ข้อมูลนักท่องเที่ยวเป็นของนงนุช** Agent และไกด์เห็นเฉพาะจำนวนผู้สมัคร ไม่เห็นข้อมูลส่วนบุคคล
8. **ทบทวนลำดับความสำคัญก่อนเริ่มทุกเฟส** (ออกเฟสใหม่ทุก 2 เดือน) เฟส 2 ถึง 4 ปรับได้ตามผลจริงหลังเปิดตัว

### 4.6 Soft launch และ Hypercare (1 มี.ค. ถึง 30 เม.ย. 2027)

- **Soft launch (มี.ค.):** ทีม WV On-call ตลอดเวลาเปิดบริการ, วิศวกรประจำหน้างาน 1 ถึง 2 มี.ค., แก้บั๊กและปรับตามผลใช้งานจริง Release ได้สัปดาห์ละครั้ง
- **Go-Live และสงกรานต์ (เม.ย.):** On-call ตลอดเวลาเปิดบริการ 1 ถึง 18 เม.ย., วิศวกรประจำหน้างาน 1 ถึง 2 เม.ย. (วันเปิดตัว) และ 13 ถึง 15 เม.ย. (สงกรานต์), Code freeze 25 มี.ค. ถึง 18 เม.ย. ยกเว้นบั๊กที่ขวางการขายหรือการสมัคร
- ประชุมสรุปทุกเช้า 15 นาที (ยอดขาย ยอดสมัคร ยอด Invite รายการผิดปกติ ปัญหา)
- ตรวจรายการ Invite ที่ระบบแจ้งว่าผิดปกติทุกวันร่วมกับทีมดูแล Agent
- แก้เฉพาะบั๊กและปัญหาการใช้งาน ไม่เพิ่มฟีเจอร์ใหม่บน Production (ทีมแยกพัฒนาเฟส 2 คู่ขนานตั้งแต่ เม.ย.)
- 30 เม.ย. 2027 ประชุมปิด Hypercare: สรุปบทเรียน กำหนดมูลค่าพ้อย และเตรียมเปิดใช้งานเฟส 2 ใน มิ.ย.

### เส้นทางวิกฤต (Critical Path)

เรื่องต่อไปนี้ถ้าเลื่อน 1 วัน วัน Soft launch จะเสี่ยงเลื่อนตาม

3. **สิทธิ์ API ระบบบัตร / ประตูเดิม (13 พ.ย.)** ถ้าไม่มีภายใน 27 พ.ย. ให้เปลี่ยนไปใช้ระบบตรวจบัตรของเราเอง (R2)
4. **ราคา กติกาบัตร กติกาพ้อยฝั่งสะสม และเงื่อนไข Agent (27 พ.ย.)** โครงสร้างข้อมูลขึ้นกับเรื่องนี้
5. **ส่ง App ตรวจ (5 ก.พ.) ทั้ง App นักท่องเที่ยวและ Agent App** ต้องเผื่อเวลาถูกตีกลับ

## 9. สถาปัตยกรรมและเทคโนโลยี

> ข้อเสนอเบื้องต้น ยืนยันหลังสำรวจระบบเดิมในเฟส 0

### หลักการ

- **Microservices แบ่งตาม domain (มติ 11 พ.ย.)** Go 8 service ในเฟส 1: Identity, Member & Point, Agent, Commerce, Ticket & Gate, Content, Notification, Report (เฟส 3 เพิ่ม Engagement, เฟส 4 เพิ่ม Partner) แต่ละ service เป็นเจ้าของ schema ของตัวเองบน MariaDB cluster เดียว ห้าม join ข้าม schema
- **สื่อสารระหว่าง service:** gRPC เมื่อต้องรอคำตอบทันที, Event ผ่าน **NATS JetStream** โดยเขียน Outbox ใน Transaction เดียวกับข้อมูล, Consumer ต้อง Idempotent, ธุรกรรมข้าม service (เช่น ชำระเงิน → ออกบัตร → พ้อย) ใช้ Saga แบบ choreography
- **API-first ตั้งแต่วันแรก** เว็บ, App นักท่องเที่ยว, Agent App (Flutter) และหน้าเว็บ Agent เข้าผ่าน **API Gateway** จุดเดียว มีเอกสาร OpenAPI รวมเป็นสัญญากลาง และสร้างโค้ดเรียก API ของ Next.js (TypeScript) และ Flutter (Dart) จากเอกสารนี้อัตโนมัติ
- **Observability ตั้งแต่วันแรก** OpenTelemetry (Trace / Log / Metric) ทุก service เพื่อตามปัญหาข้าม service ได้
- **CMS เขียนเองใน Go + Next.js** (มติ 9 พ.ย.) ใช้ฐานข้อมูลและระบบสิทธิ์ / Audit log ชุดเดียวกับ Admin ทำเฉพาะชนิดเนื้อหาที่เฟส 1 ใช้จริง ไม่ทำ Page builder
- ใช้บริการสำเร็จรูปที่ได้มาตรฐาน (Payment, อีเมล, SMS, Push) แทนการสร้างเอง
- หน้าที่นักท่องเที่ยวจีนใช้ (สมัครสมาชิก, Invite, ซื้อบัตร) ต้องไม่พึ่งบริการที่ถูกบล็อกในจีน เช่น Google Fonts, reCAPTCHA, Google Maps หรือ Firebase SDK (ใช้ Cloudflare Turnstile แทน reCAPTCHA) เพราะซิมจีนที่โรมมิ่งมาไทยยังส่งข้อมูลผ่านเครือข่ายในจีน
- ทุกอย่างอยู่ใน Cloud ในนามนงนุช มี Infrastructure as Code เพื่อส่งมอบได้

| CDN / WAF | **Cloudflare** วางหน้า Cloud ทุกรูปแบบ, บัญชีในนามนงนุช | Cache รับ Traffic พีค, WAF กันการโจมตี, Rate limit และ Turnstile กันบอทสมัครบัญชีปลอม (R14), ไม่ใช้ Waiting room ของ Cloudflare (พัฒนาเอง), ต้องทดสอบความเร็วจากซิมจีนที่โรมมิ่ง (R15) |
| Push notification | **Firebase Cloud Messaging (FCM)** + **Huawei Push Kit** | FCM ส่งถึง iOS (ผ่าน APNs) และ Android ที่มี Google services, Huawei Push Kit ส่งถึงมือถือ Huawei ที่ไม่มี Google services (นักท่องเที่ยวจีนใช้มาก), เรื่องสำคัญส่งซ้ำผ่าน LINE / อีเมล / SMS |
| App Store | App Store, Google Play และ **Huawei AppGallery** | Flutter Build 2 แบบจากโค้ดเดียว: GMS (Google Play) และ HMS (AppGallery), การเผยแพร่ใน AppGallery ประเทศจีนต้องตรวจเงื่อนไขกับ Huawei [รอยืนยัน, ดู #24] |
| Waiting room | **พัฒนาเองใน Commerce service + Next.js** | ควบคุมกติกาการปล่อยคิวเองได้, ไม่ขึ้นกับแพ็กเกจ Cloudflare, ทำงานร่วมกับ Rate limit ของ Cloudflare |
| Deploy | Container (Docker) ต่อ service ผ่าน CI/CD, Infrastructure as Code | ใช้ได้กับ Cloud ทั้ง 3 รูปแบบ, ย้ายผู้ให้บริการได้ภายหลังโดยไม่ต้องแก้โค้ด, ส่งมอบให้นงนุชได้ |
| Payment | KBank Payment Gateway (ตามโครง App, รอยืนยัน) รองรับบัตร + PromptPay และได้ PCI DSS | เงินเข้า Merchant นงนุช, ใช้ได้ทั้งเว็บ App และ Scan จ่ายเงินในสวน |
| Monitoring | Uptime monitor + Error tracking + Crash reporting + Log รวมศูนย์ | รองรับ SLA 99.5% |
| Animation | GSAP ScrollTrigger หรือ Framer Motion (ตาม Interaction Spec ในต้นแบบ) | Scroll และ Motion ตามดีไซน์, รองรับ prefers-reduced-motion |

### 9.1 รูปแบบ Cloud (เสนอ 3 ทางเลือก)

ระบบออกแบบให้ทำงานได้เหมือนกันทั้ง 3 รูปแบบ (Docker + Infrastructure as Code, Cloudflare วางหน้า) ผู้บริหารเลือกตามความพร้อมของทีม IT นงนุชและงบประมาณ [ตัดสินใจภายใน 27 พ.ย., ดู #23]

| หัวข้อ | 1. เช่า Cloud จาก Partner ของ WV | 2. นงนุชดูแล Server เอง | 3. WV ดูแลทั้งหมดบน Wisdom Cloud |
|---|---|---|---|
| ผู้เช่า / เจ้าของสัญญา Cloud | นงนุชเช่าตรงกับบริษัท Partner (WV แนะนำและช่วยตั้งค่า) | นงนุช (Server ของนงนุชเอง หรือ Cloud ที่นงนุชเช่าเอง) | WV (นงนุชจ่ายค่าบริการรายเดือนให้ WV) |
| ผู้ดูแลระบบ (OS, ฐานข้อมูล, Backup, Patch, Monitoring) | WV ดูแลตามสัญญา SLA, Partner ดูแลฮาร์ดแวร์และเครือข่าย | ทีม IT นงนุช, WV Deploy แอปและช่วยแก้ปัญหาตามที่ตกลง | WV ทั้งหมด |
| SLA 99.5% (หัวข้อ 12) | WV รับผิดชอบ, ขึ้นกับ SLA ของ Partner | แยกส่วน: WV รับผิดชอบตัวแอป, นงนุชรับผิดชอบ Server / เครือข่าย | WV รับผิดชอบทั้งหมด จุดติดต่อเดียว |
| ข้อดี | สมดุลระหว่างความเป็นเจ้าของและภาระงาน, ขยายเครื่องช่วงพีคได้ง่าย | นงนุชควบคุมเต็มที่, ไม่มีค่าบริการดูแลรายเดือนให้ WV | เร็วที่สุด, นงนุชไม่ต้องมีทีม Server, ปัญหาจบที่ WV |
| ข้อควรระวัง | ต้องตกลงขอบเขตความรับผิดชอบระหว่าง WV และ Partner ให้ชัด | ทีม IT นงนุชต้องพร้อมดูแล 24 ชม. ช่วงเปิดตัว, ขยายเครื่องช่วงสงกรานต์อาจช้า, ต้องพร้อมภายใน ม.ค. เพื่อ Load test | ขัดกับหลักการข้อ 1 เรื่องบัญชีในนามนงนุช จึงต้องมีข้อสัญญาเรื่องข้อมูลและการย้ายออก |
| ข้อกำหนดที่ต้องมีทุกรูปแบบ | Data Center ในประเทศไทย, ข้อมูลเป็นของนงนุช, นงนุชขอ Backup / Export ข้อมูลได้ทุกเมื่อ, แผนย้ายออก (Exit plan) พร้อมระยะเวลาส่งมอบ, Production พร้อมก่อน W11 (14 ม.ค.) เพื่อ Load test | | |

> WV เสนอราคาและสเปกเครื่อง (ช่วงปกติและช่วงพีค) ของทั้ง 3 รูปแบบ ให้ผู้บริหารเปรียบเทียบก่อน 27 พ.ย. ระหว่างรอ ทีมพัฒนาใช้ Staging ชั่วคราวของ WV

## 12. ความปลอดภัย PDPA และ SLA

### SLA

| หัวข้อ | ข้อตกลง |
|---|---|
| Uptime | ไม่ต่ำกว่า 99.5% ต่อเดือน |
| ปัญหาวิกฤต (Critical) | ตอบสนอง 1 ชม. แก้ไข 4 ชม. |
| ปัญหาสูง (High) | ตอบสนอง 4 ชม. แก้ไข 1 วันทำการ |
| ปัญหาปกติ | ตอบสนอง 1 วันทำการ แก้ไขตามรอบ Release |
| รายงานประจำเดือน | ภายใน 7 วันทำการหลังสิ้นเดือน |

### ความปลอดภัย

- ไม่เก็บข้อมูลบัตรเครดิต ใช้ Gateway มาตรฐาน PCI DSS
- เข้ารหัสข้อมูลระหว่างส่ง (TLS) และขณะจัดเก็บ รวมเอกสารนิติบุคคลของ Agent
- CMS ใช้ 2FA ทุกบัญชี สิทธิ์ตามบทบาท และบันทึก Audit log
- จำกัดอัตราการขอ OTP และการสมัครต่อเครื่อง / IP / ไกด์ เพื่อกันบัญชีปลอมและค่า SMS บานปลาย
- Secret เก็บใน Secret manager ไม่อยู่ในโค้ด
- Backup รายวัน เก็บ 30 วัน ทดสอบกู้คืนทุกไตรมาส

### PDPA

- ทำ DPA ระหว่างนงนุช (ผู้ควบคุมข้อมูล) และ WV (ผู้ประมวลผลข้อมูล)
- ข้อมูลหลักเก็บใน Data Center ในประเทศไทย (ทุกรูปแบบ Cloud), ระบุ Cloudflare (ข้อมูลผ่านเครือข่ายต่างประเทศระหว่างส่ง) Firebase (Device token สำหรับ Push) และ Tencent / WeChat (ข้อมูล Login ที่ผู้ใช้ยินยอมให้) เป็นผู้ประมวลผลข้อมูลช่วงในนโยบายความเป็นส่วนตัว
- ขอความยินยอมแยกสำหรับการตลาด (ไม่ติ๊กไว้ล่วงหน้า), มี Cookie consent, ข้อความขอความยินยอมครบ 7 ภาษา
- Agent และไกด์ไม่ได้รับข้อมูลส่วนบุคคลของนักท่องเที่ยว เห็นเฉพาะจำนวน
- นักท่องเที่ยวต่างชาติ (รวมจีน) ได้รับแจ้งว่าข้อมูลจัดเก็บและประมวลผลที่ใด [ฝ่ายกฎหมาย NN ตรวจข้อกำหนดของประเทศต้นทางที่เกี่ยวข้อง]
- เลขบัตรประชาชน / พาสปอร์ตใช้เพื่อเช็กสิทธิ์ราคาและกันบัญชีซ้ำเท่านั้น: เข้ารหัสระดับฟิลด์, ตรวจซ้ำด้วย Hash, แสดงแบบปิดบัง (4 หลักท้าย) ทั้งใน App, e-Ticket และ CMS ยกเว้นบทบาทที่ได้สิทธิ์, ระบุวัตถุประสงค์ในนโยบายความเป็นส่วนตัว 7 ภาษา
- เก็บข้อมูลเท่าที่จำเป็น รูปผู้ถือบัตรรายปีใช้เพื่อตรวจบัตรเท่านั้น, เอกสารนิติบุคคลของ Agent ใช้เพื่อตรวจสอบเท่านั้น
- วันเกิดใช้เพื่อสิทธิ์ตั๋วฟรีวันเกิด, Social login ขอเฉพาะข้อมูลที่จำเป็น (ชื่อ อีเมล)
- ผู้ใช้ขอดู แก้ไข หรือลบข้อมูลได้ (ลบบัญชีเองใน App / เว็บ ดำเนินการภายใน 30 วัน), เก็บ Consent log ทุกครั้งที่ให้หรือถอนความยินยอม
- แจ้งเหตุข้อมูลรั่วไหลแก่นงนุชภายใน 24 ชม.
